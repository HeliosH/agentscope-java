# 企业模型流中断自动恢复设计与实施

## 1. 目标

企业内部模型服务可能在已经返回部分内容后因网络、网关、推理服务重启或连接空闲超时而中断。用户不应被迫手工点击“重试”或“继续”，系统需要在不重复执行工具副作用的前提下，自动恢复当前 Agent 回合，并最终返回完整结果。

本方案只处理模型响应流的瞬时中断。权限拒绝、参数校验、工具执行失败、业务异常和用户取消仍然按原有流程结束任务，避免把确定性错误误判为可恢复错误。

## 2. 设计原则

1. **流式输出一次提交**：模型首次返回内容后不再使用底层 `retryWhen` 重放同一条响应流，否则已经展示给用户的前缀会被重复拼接。
2. **回合级恢复**：中断后重新执行当前 Agent 回合，而不是简单重放 HTTP 请求。首次尝试携带用户消息，后续尝试使用空输入，让 Agent 从已写入的会话状态继续。
3. **工具幂等优先**：模型中断发生在模型流阶段，工具尚未提交时才允许自动恢复；工具、权限或业务错误不进入该路径。
4. **结果原子落库**：只有整个回合成功后才写入 assistant 最终消息并标记运行成功，半截内容不作为最终答案持久化。
5. **部署可控**：恢复策略通过配置开关和参数控制，支持按环境调整，不把企业模型的故障特征写死在代码中。

## 3. 端到端流程

```text
用户请求
   |
   v
SaaSChatController 创建/复用 Run
   |
   v
Agent.streamEvents(用户消息) ----> ModelUtils
   |                                  |
   |                                  +-- 首个响应前失败: 按模型调用重试
   |                                  |
   |                                  +-- 已有响应后失败: 标记为
   |                                      ModelStreamInterruptedException
   v
AG-UI 已输出的半截消息
   |
   v
run_recovering 事件 + 指数退避
   |
   v
清理前端半截消息，重新订阅 Agent（空输入）
   |
   +---- 成功 ---> 写入完整 assistant 消息，Run=SUCCEEDED
   |
   +---- 再次中断且未超过上限 ---> 继续退避恢复
   |
   +---- 超过上限/非中断异常 ---> Run=FAILED，返回 error 事件
```

一次请求内的恢复不会创建新 Run、新会话或新用户消息，也不会重新创建父 Agent 的沙箱。Agent 上下文、父子 Agent 关系和本次任务的 workspace 继续复用原运行上下文。

## 4. 分层职责

### 4.1 模型层

`ModelUtils.applyTimeoutAndRetry` 将超时和模型调用重试分成两个阶段：

- 在模型尚未产生第一个响应项前，网络连接失败、网关瞬时错误和超时可以按 `ExecutionConfig` 重试。
- 一旦产生过响应项，后续错误包装为 `ModelStreamInterruptedException`，并禁止底层重新订阅，保证不会重复消费已经发送的 token。

这个边界适用于流式和非流式模型，模型供应商的错误类型仍由原有 `retryOn` 策略决定。

### 4.2 SaaS 运行层

`SaasChatController` 负责回合级恢复：

- 首次尝试传入用户消息。
- 后续尝试传入空消息列表，使用 Agent 已更新的上下文继续。
- 只捕获 `ModelStreamInterruptedException` 的异常链。
- 通过指数退避降低内部模型网关恢复期间的并发压力。
- 发送 `run_recovering` AG-UI 自定义事件，让客户端清理半截回答并切换到恢复状态。
- 全部尝试耗尽后沿用原有失败持久化和错误返回路径。

### 4.3 前端层

SSE 解析器识别 `run_recovering` 事件。聊天面板收到该事件后清空当前未完成的 assistant 内容和工具展示，随后接受恢复尝试产生的新事件。用户看到的是一次连续任务，而不是两个拼接的回答。

### 4.4 持久化层

用户消息在回合开始时按原有 session/run 逻辑保存；assistant 消息只在最终成功后保存。恢复事件是运行过程事件，不作为最终 assistant 消息写入。运行最终状态保持单一 Run 的 `SUCCEEDED` 或 `FAILED`，便于审计、重连和统计。

## 5. 配置

配置前缀为 `saas.model.stream-recovery`：

| 参数 | 默认值 | 作用 |
| --- | ---: | --- |
| `enabled` | `true` | 是否启用回合级自动恢复 |
| `max-attempts` | `3` | 包含首次调用在内的最大尝试次数 |
| `initial-backoff-millis` | `1000` | 第一次恢复前等待时间 |
| `max-backoff-millis` | `10000` | 退避时间上限 |

对应环境变量为 `SAAS_MODEL_STREAM_RECOVERY_ENABLED`、`SAAS_MODEL_STREAM_RECOVERY_MAX_ATTEMPTS`、`SAAS_MODEL_STREAM_RECOVERY_INITIAL_BACKOFF_MILLIS` 和 `SAAS_MODEL_STREAM_RECOVERY_MAX_BACKOFF_MILLIS`。

建议生产环境先使用 `max-attempts=3`，观察模型网关的中断比例、恢复成功率和平均延迟后再调整。对已知不稳定的模型，可以通过模型路由配置降低并发或切换备用模型；不要无限增加重试次数。

## 6. 一致性与安全边界

- **不会重复用户消息**：控制器只在首个 Agent 订阅传入用户消息，恢复订阅使用空输入。
- **不会重复半截回答**：模型层禁止中断后的底层重试；AG-UI 事件转换器在恢复前重置消息状态。
- **不会重复工具副作用**：工具调用错误不触发模型流恢复。若未来支持工具执行中断恢复，必须增加工具调用幂等键、执行日志和结果去重。
- **不会误恢复权限错误**：恢复条件检查完整 cause chain，只接受 `ModelStreamInterruptedException`。
- **不会把失败内容当成功结果**：assistant 最终消息和成功状态仍在完整事件流结束后提交。
- **客户端断线可恢复**：原有运行事件回放和 durable run 机制继续生效；本次回合内恢复由服务端执行，不依赖浏览器保持连接。

## 7. 观测与验收

应至少监控以下指标：

- 模型流中断次数及按模型、租户、错误类型分布。
- 自动恢复触发次数、恢复成功率、最终失败率。
- 每次恢复等待时长和整个 Run 的额外耗时。
- 中断后是否产生重复 tool call、重复 assistant message 或状态不一致。

本次实现已增加定向测试，验证模型在已经输出部分内容后发生错误时只订阅一次底层流，并向上抛出 `ModelStreamInterruptedException`；SaaS 应用和前端生产构建均已通过。

## 8. 后续生产化增强

当前回合级恢复解决了最常见的“模型已输出但流断开”问题。若要覆盖服务进程在恢复等待期间崩溃、跨实例迁移和长时间离线，需要将 `RECOVERING` 状态、恢复次数、下一次执行时间和恢复原因写入 durable run/attempt，并由现有调度器领取恢复任务。该增强必须配合 Agent 状态快照、工具幂等和 sandbox workspace checkpoint 一起上线，不能只把 HTTP 重试搬到后台。
